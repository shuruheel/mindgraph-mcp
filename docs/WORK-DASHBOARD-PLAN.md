# MindGraph work dashboard implementation plan

**Proposed pilot · 2026-11-27.** The first release is one user story proposed, revised, approved, executed, and reviewed in the browser. Its home is the existing Project board. Begin with the Memory quality lane in an internal Project that already has a hosted agent and a repository grant. Keep the current one-repository change-card and human merge rules.

**Try the review.** Open the [interactive story card](work-dashboard/story-review.html). Open its citation, inspect all three branches, attach feedback to the unavailable-source branch, submit the change request, review the prepared revision alongside the prior version, approve it, and reveal the simulated run evidence in the acceptance chart and table. Reload to try approving the original instead. The counts are fixture data. The cloud implementation and user pilot are delivery gates below.

## Wireframes for product review

Open the [dashboard and Omarchy wireframes](work-dashboard/wireframes.html) at the agent activity feed. Preview an incoming milestone, filter for open decisions, and answer a worker’s question. Return to the full feed to see its thread and evidence from completed work. The Objective view demonstrates directing two lanes in chat and reversing the change from the receipt. The Omarchy view shows signed-out and connected launchers, a local handoff, and a configurable shell-plugin preview with six widgets. The Flow diagrams view traces destinations and the approval-to-evidence lifecycle. These specimens use fictional data.

**Home is a streaming feed of meaningful agent updates.** Lead with blockers, questions, approval requests and milestone evidence. Order the full feed by recency, keep a persistent **Needs you** count and filter, and group repeat updates by story and event. An unanswered question in an active lane stays actionable however much progress arrives. Show new arrivals behind a “Show new updates” control while someone is reading so grouped or incoming events never jump the viewport. Routine heartbeats and tool calls belong inside run detail. On a quiet day show recent delivered outcomes. On a new account, offer to describe the first objective in chat.

**A clear chat instruction acts immediately and returns a receipt.** Name affected lanes, actual worker status, work that still cannot start, and a direct link to reverse the state change. Ambiguous references, hypotheticals, and questions never mutate state; they call for clarification. Ordinary conversation and story approval retain distinct actions.

| Uncertainty to test before visual polish | What to watch |
| --- | --- |
| Feed urgency | Can someone decide which of a blocked worker and a pending approval to address first? Try an item age, number of stories waiting, and worker owner before introducing priority scores. |
| Meaning of approval | Can someone explain the difference between approving the proposed behavior (authorizing execution) and reviewing the measured evidence + draft PR to merge on GitHub? Test action labels and show the destination after each click. |

## Shared vocabulary

A user story is the day-to-day deliverable. The board presents each story as a **Card**, using the existing specification, approval, run, and review flow. A lane can stay active for as long as people want to invest in it.

| Concept | What it tells the person |
| --- | --- |
| **Objective** | The outcome they want and how they will tell whether it improved. |
| **Lane** | An ongoing stream of work contributing to one or more objectives. It shows which stories are underway, what they delivered, and where progress is blocked. An objective can draw on several lanes. |
| **User story** | One useful change with a beneficiary, an outcome, and observable acceptance criteria. Its card is where a person approves the specification and reviews the result. |
| **Story specification** | The context that defines a story for the person reviewing it and the agent carrying it out. A diagram can specify behavior, a mockup can specify an interaction, and a chart can specify how success will be measured. |
| **Task and run** | A task describes work an agent can perform. A run records an attempt. Technical steps or retries can contribute to a story without counting as additional deliveries. |
| **Measure** | Evidence of whether delivered stories improved the objective, such as how often recall returns the right decision and source. |

The current board uses **Needs you · Backlog · Queued · In progress · Review · Done**, within an Organization and Project. Local coding-tool tasks retain their existing meaning. The dashboard design below uses the story card as the unit of delivery and keeps the current board labels.

The MindGraph roadmap already uses “Q — Memory quality” and “A — Objective-driven agents” for standing streams that span repositories. Today the board supports card ordering and a dependency link. A dashboard lane and its relationship to objectives are proposed additions.

## First release — one visually approved story

The beneficiary is an engineer returning to a repository. The story is “I can open the source behind a recalled decision and tell when the cited revision is unavailable.” Implement the citation behavior in a granted fixture repository. A hosted worker should finish the exercise with the laptop closed. Use an existing objective and agent for this first pilot.

| Review panel | Required behavior in the first release |
| --- | --- |
| Interaction mockup | Show a recalled decision with a citation. Activating it shows the highlighted passage, revision, and file. The person can inspect the intended interaction before approval. Rendered from a declarative JSON component spec by trusted dashboard components (never arbitrary agent-authored HTML/JS in the dashboard origin; any future HTML preview requires a credential-less `<iframe sandbox>` with strict CSP). |
| Behavior diagram | Show the available, renamed, and unavailable branches with uniform visual emphasis. The reviewer can attach one or more comments to any branch before submitting a change request. A revised proposal opens at its changed branch and retains the original comments and prior branch text for side-by-side comparison. |
| Acceptance chart | Show baseline, target, denominator, fixture version, and the equivalent table. For this scenario the baseline is two correct outcomes in three cases and the target is three. After execution, show a **Measured** bar beside the target and a per-case Measured column in the table. An unmeasured baseline reads “Not measured.” |

Markdown holds the narrative and acceptance criteria in v1 alongside a pinned manifest for typed panels, stable element IDs, and asset digests. The pilot requires all three panels for this story; simple or historical stories can have fewer. Let the reviewer approve once, with source material and long prose available on demand. Support keyboard navigation and text equivalents. Add video, audio and time-based annotations later through the same manifest.

**Interaction to validate with people.** Hand reviewers the prototype with the prompt “An unavailable citation must never appear to point at a verified source. Decide whether to approve this story.” Keep all three branches styled identically with per-branch feedback controls so the test measures genuine comprehension rather than button-hunting. Observe whether reviewers identify the problematic branch, submit the change request, see what changed against revision 1, and distinguish target from measured evidence without opening a long document. Proposed pilot bar: four of five representative reviewers complete all four steps without coaching. Record where the others hesitate and revise the panel before widening the pilot. The browser automation checks mechanics; this exercise checks comprehension.

## Story revision and runner contract

The following records and command names specify proposed semantics. Extend the existing board API and Supabase change-card records in the owning repositories. Keep the graph’s Task UID as the card identity and its board state as the shared view.

**Canonical manifest schema (v1).** Hash the RFC 8785 canonical JSON of `{schema_version: 1, narrative_md, acceptance_cases: [{id, label, baseline, target}], panels: [{id, kind, element_ids, accessible_text, content, assets: [{path, sha256}]}], fixture_ref}` where `kind` is one of `interaction_mockup | behavior_diagram | acceptance_chart`, `content` is a typed declarative payload (no executable script strings), and each referenced file is pinned by SHA-256. Exclude transient download URLs, comments, and run results from the manifest.

| Record | Data and ownership |
| --- | --- |
| Submitted story revision | Cloud stores an immutable revision ID, parent ID, organization, Project, card UID, repository grant reference, canonical manifest payload, and `manifest_digest`. Apply the card’s grants to every asset read. |
| Annotation | Store actor, card, revision, panel, optional element, review submission ID, and message. Reviewers may stage multiple element-anchored comments before submitting a change request. Edits create a new proposal; earlier annotations stay anchored to what their author saw. |
| Approval | Store member identity, approved revision ID and manifest digest alongside the existing frozen repository and acceptance checks. The current submitted revision is the approval precondition. A stale tab receives a `409 Conflict` with the changed panels. Duplicated approval with the same request key and payload returns the existing receipt (including a `superseded_by` pointer if a newer revision later replaced it); reusing a request key with different inputs returns `409 Conflict`. Retain request keys for at least 24 hours. |
| Assignment and evidence | Record card, approved revision and digest on the existing assignment. At claim, the bound worker fetches that revision, verifies each defining asset and reports the digest and case IDs with its checkpoint. The independent evaluator resolves acceptance fixtures from an immutable `fixture_ref` digest outside the worker’s writable diff (or fails closed if the worker’s tree modifies any pinned fixture path relative to `tested_base_commit`), then records measured outcomes, evaluator/fixture versions, and tested commit or tree digest. Keep the original target frozen. |

**A change during execution.** Drafting a new revision can coexist with an active run. Explicitly submitting a replacement for execution makes the old approval ineligible for new claims or publication. An in-flight worker may record its last checkpoint and evidence against its old revision. It needs a fresh approval and assignment to execute the replacement. A purely conversational reply or a new measurement attaches to the existing revision. A changed required behavior, target, repository or defining asset makes a new revision.

| Operation | Server behavior to implement and test |
| --- | --- |
| Draft, comment, and request changes | A planner or authorized member creates a draft and submits it for review. A reviewer can attach one or more element-anchored comments, then submit **Request changes**, transitioning the revision to `needs_revision` and queuing a planner revision job (or allowing an authorized member to submit `r2` directly). Return the new board version and permitted actions. Only a signed-in authorized member approves the pilot story. |
| Approve | Check membership, card scope, expected board version, submitted revision, repository grant and availability of defining assets. Atomically persist the approval and runnable change state. Reserve the same idempotency key for the same payload; reject reuse with different inputs. |
| Claim and publish | Extend the current compare-and-swap transition to require the approved revision and an active lane. Bind it to the existing session. Recheck revision, lane, grant, bound session and tested tree before issuing a publish intent. If the target branch advanced since `tested_base_commit` and causes a merge conflict, either rebase and re-evaluate against the frozen manifest or hold in a retryable conflict state—never publish an unevaluated merge. Use the existing reconciliation path after a crash. Guard every mutation path into board-managed work: direct writes through `mindgraph_plan` or general SDK plan routes targeting a board-managed card must fail closed with a structured policy error pointing to the board API. |
| Display and complete | Read the card, annotation, approval, run and evidence from one permission-filtered view. Release 1 has two human gates: approving the story specification (authorizing execution) and reviewing measured evidence + the draft PR to merge on GitHub. A failed case stays visible with its evidence and permits a new proposal. A successful evaluation leads to Review and the existing draft PR flow; the GitHub merge event closes the change card. |
| Storage failure or race | Keep approval and dispatch authorization in the same transactional store. Treat graph and inbox updates as retryable projections keyed by card and version. A missing panel, tampered fixture, superseded revision, or unavailable grant holds execution and gives the user an actionable reason. Temporary service failures are retryable. |

**Contract fixture for implementation.** Use card `citation-source`, revisions `r1` and `r2`, panel `source-behavior`, element `unavailable`, and case IDs `available`, `renamed`, `unavailable`. The proposed approval request carries `{card_uid, revision_uid, manifest_digest, expected_version, request_key}`. Resolve organization and actor from authenticated context. The claim response contains `{run_uid, card_uid, revision_uid, manifest_digest, manifest_ref, tested_base_commit, fixture_ref}`. The evaluator attaches `{run_uid, revision_uid, manifest_digest, tested_tree_digest, fixture_digest, case_results, evaluator_version}`. A successful replay returns the same receipt. An obsolete version or request-key collision returns a conflict. A denied actor receives the existing access-denied response without exposing other organizations’ IDs.

The board freezes acceptance criteria on approval, the managed-agent claim path checks its bound session, and the repository loop persists side-effect intents and reconciles them. Carry revision identity through these paths. ## Lanes, objectives, and conversations

**Memory quality** can stay open across many objectives. For the objective “Help engineers trust recalled decisions,” one story might read, “As an engineer returning to a repository, I can open the source for a recalled decision.” For acceptance, selecting the citation must open the expected source revision for each agreed test case. The board can show that story as delivered while another story, “Recover a decision after its source file moves,” is blocked on examples of renamed files. The lane continues after both stories ship.

| Surface | Proposed behavior |
| --- | --- |
| Graph and cloud | Give a lane a stable ID, name, purpose, and active or suspended state. Link it to the objectives it serves. Associate a story card with a primary lane for the board view and retain its objective, specification, acceptance evidence, and current status. Existing cards can appear without a lane. Resuming a suspended lane reuses its ID and history. |
| Dashboard | From an objective, show its contributing lanes. For each lane show the current stories, a recently delivered story with evidence, and the blocker with who can resolve it. Include the relevant outcome measure and its observation period where available. A count such as “3 stories delivered this month” has a clear meaning for an ongoing lane. A lifetime percentage complete has no denominator. |
| Board controls and chat | Expose **Start lane**, **Suspend**, and **Resume** on the board and through signed-in chat. “Pause Memory quality and start Import reliability” resolves named lanes via a deterministic command schema and applies the same authorized commands as the controls. Only unambiguous single-match imperative user turns execute immediately; questions, hypotheticals (“what if we paused…”), and ambiguous targets ask for clarification. Untrusted story, PR, or memory text in context must never invoke lane commands. Return a receipt naming affected lanes, actual worker status, what can/cannot run, and a direct **Reverse change** link. |
| Scheduling | Starting a lane makes its approved, ready stories eligible for scheduling. Story approval remains a separate decision. On suspension, hold queued stories and prevent new runs from starting, including retries. Let an active attempt finish its current bounded step and save its checkpoint. Hold the next tool action or publication, show it as pausing until acknowledged, and preserve its evidence. Items already in review remain reviewable. On resume, recheck approvals, blockers, and dependencies before dispatch. Serialize suspension with claims and deduplicate repeated chat commands. |

**Demonstration.** With one Memory quality story delivered, one running, and one blocked, ask in chat to suspend that lane and start Import reliability. The board should show the delivered evidence, paused work, and outstanding question on Memory quality. A ready, approved story in Import reliability can start. Repeating the same network request must preserve one lane and one run; clicking **Reverse change** restores the prior lane states cleanly. Resume Memory quality from the board and verify that its open question still blocks the affected story.

**Race and idempotency rule.** Persist the lane status, version, and effective suspension time in the scheduler’s transactional store. Check it while claiming and when issuing a new external action. A claim committed first may checkpoint. A suspension committed first holds the claim. Reconcile an already-issued external action and report its actual outcome. An unresponsive worker shows “Waiting for worker” until lease expiry, then “Suspended.” Resuming wakes eligible work once. A two-lane chat command records both state changes in one transaction with the member’s authority and a `client_message_id` / `command_batch_id` replay key (never hashing raw English text, so an intentional repeat hours later still executes while network retries deduplicate).

**Blocker lifecycle and suspended-lane policy.** On a story, a reviewer can answer a question in the existing card thread. Record the blocker’s ID, `blocking_episode`, affected story, answer, and worker acknowledgement. Submitting an answer moves the blocker to **Answered · Awaiting acknowledgement** and removes it from immediate **Needs you** urgency; if the worker rejects/clarifies the answer or its acknowledgement lease expires without progress, Cloud opens a new `blocking_episode` and returns it to **Needs you**. An unresolved dependency still holds the story. When a lane is **Suspended**, its open blockers remain visible in lane detail and the full activity feed (badged as `Paused lane`), suppress desktop interruptions, and do not inflate active **Needs you** urgency until the lane resumes.

**Views and activity feed.** Let the user state an objective in chat. Use the current authorized Project and its eligible agent when unambiguous. Surface a missing execution destination only when work needs to run. Objective detail groups story cards by lane. Lane detail shows open stories, last delivered evidence and who can clear each blocker. Give returning users an activity feed on Overview and keep onboarding available. Stream authorized board/run events over SSE with cursor-based polling fallback, sourcing actionable state from the existing inbox read. Include event ID, monotonic cursor, story, lane, timestamp, actionable state, and evidence link. Deduplicate replayed events on reconnect; if a cursor has expired, perform a clean snapshot resync. Recompute actionability from current story, blocker, and lane state. Group repeat updates by `(story, event)` behind “Show new updates” while the user is reading so the list never jumps. Deep-link each event to its revision, question or result. **Interruption rule.** An open blocker may raise a desktop notification when work has actually stopped, the lane is active, and the signed-in person is the required responder. A routine approval, a milestone, or work waiting on another worker updates its widget and feed quietly. Approvals that become actual blockers follow the blocker rule. Deduplicate by organization, blocker ID and blocking episode across reconnects and widgets. Answering in the browser updates the desktop. Dismissing a notification leaves the question open. Respect user notification preferences and desktop quiet mode, then recheck eligibility before delivering a delayed alert. Clicking an alert opens its thread. Hiding the Blockers widget and muting interruptions are independent choices.

**Implementation and release.** Run a single user-level device-authorized source (either a native `omarchy-shell` service module or a `systemd --user` helper exposing summaries over a user-private Unix domain socket or D-Bus—never TCP port 18790) that serves all six widgets, shares the locked token store, and handles sleep/wake reconnect and token expiry gracefully. Cloud returns the same permission-filtered IDs, states and destinations as the dashboard feed. Stop subscriptions and clear visible data on disconnect. Start with Blockers and its notification path, then add the other five summaries against the same contract. Verify native notification activation, dismiss, quiet mode, expiry, sleep/wake recovery, and cross-surface updates in a real desktop session. In the wireframe, select **Omarchy → Connect**, choose widgets, and compare **Preview blocker event** with **Preview progress event**. Replaying the same blocker should leave a single interruption. Answer it and verify its thread remains accessible with the updated status.

## Acceptance and rollout

**Runnable design check.** With Chromium and a matching ChromeDriver installed, run `python3 docs/work-dashboard/check-review.py` from this checkout. It exercises both [story-review.html](work-dashboard/story-review.html) (original and revised approval paths, uniform branch selection, multi-comment feedback, prior-version comparison, post-run measured chart/table rendering, keyboard focus, and narrow layout) and [wireframes.html](work-dashboard/wireframes.html) (feed filters, incoming milestone reveal, blocker answer retention, chat lane switch + reverse undo, Omarchy widget toggles, blocker deduplication, and disconnect cleanup). It uses a temporary browser profile. The example asset and measurements are local to the specimen.

**Staging end-to-end scenario.** Seed a private org, one authorized member, an agent with a GitHub fixture-repo grant, a Memory quality lane, a story and three deterministic citation cases. Enable the work dashboard for that org. All counts below are test fixture expectations.

1. Open revision 1. Attach feedback to the unavailable branch and submit the change request. Assert the thread targets the exact element and no assignment is runnable.
2. Submit revision 2. In the old tab try to approve revision 1. Expect a `409 Conflict` with the replacement reference. Inspect the changed branch in the fresh tab, approve revision 2 twice with the same request key, and observe one approval and one assignment. Verify reusing that request key with a different revision returns `409 Conflict`.
3. Close the browser. Have the bound worker load the frozen manifest, report its digest and run the three cases. Validate a missing asset or a worker edit to a pinned fixture path stops execution/evaluation. In a separate run change the proposed fallback after claim and verify the old run cannot publish the replacement.
4. Reopen the card. Check approval digest equals runner digest, evidence is pinned to the tested tree and `fixture_digest`, and measured case results and target are separately visible. A failing fixture stays reviewable. The passing fixture opens a draft PR for the evaluated tree. Merge in the test repository and observe one Done transition.
5. Repeat the protected operations with a read-only member, another organization, an unbound runner, and a direct `mindgraph_plan` write against the board-managed card. Verify permissions and write fencing on the card, raw asset, evidence and inbox reads as well as on claims and writes. A local standalone task retains its existing behavior.

**Operational gates.** Log correlation IDs for the org, card, revision, approval, run and publish intent. Monitor claim conflicts, evidence with a mismatched revision or tampered fixture, held stories, duplicate dispatch and time to first checkpoint. Omit credential values, private paths and story bodies. Roll out additive storage and backward-compatible reads first. Legacy cards retain frozen criteria, history and existing review. Require the revision contract for pilot cards on every worker path, including older clients. Run read-only comparison of board state before enabling dispatch. To roll back, disable new visual-story submissions and claims, drain or fence active pilot work, reconcile publication intents, and retain readable historical approvals and evidence.

## Out-of-scope extensions

| Deferred | What it would take |
| --- | --- |
| Promoting local tasks onto the Project board | After repository identities converge, define when a local task becomes a proposed story card and how it enters the board’s approval flow. |
| **Open on this computer** from a dashboard card | A `mindgraph://` link handler and a read of one card for device credentials. Requires repository identity resolution and a matching local checkout. |
| One card spanning several repositories, with approval covering the specification only and scope set by the agent’s repository access | Replacing the one-change-per-card record across staging, publishing, pull request lookup, and measures, and ending the rule that approval freezes a repository. The repository-agents specification names the first part as its next slice, so both belong there. |
| Automatic execution in a brand-new organization | Provide a default execution destination and an authorized repository grant. Until then, the user can discuss an objective and save a draft. |
| Handing an agent’s card to a local tool | Its own specification. It conflicts with the rule that the published code is exactly the code that was checked. A person can already release or dismiss an agent’s card and write their own. |
| Approving several cards at once | The repository-agents specification cut it. Reopen only if single approval proves slow in use. |
